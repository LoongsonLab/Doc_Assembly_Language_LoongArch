#	操作系统加载ELF文件

在LoongArch架构中，操作系统加载并运行一个ELF文件，主要通过`execve()`系统调用触发。整个过程从内核态的解析和加载开始，再由用户态动态链接器接管，最终跳转到程序入口点。

##	系统调用入口

在Shell中输入一个命令后，Shell会通过`fork()`创建一个新进程，然后在新进程中调用`execve()`系统调用，并传递程序路径和参数。在内核中，这会触发一系列调用链，最终进入内核的二进制格式处理程序（binfmt）。

`execve()`调用链：`sys_execve()` -> `do_execve()` -> `search_binary_handler()` -> `load_elf_binary()`。

在这个调用过程中，Linux内核会销毁当前进程的旧地址空间，并用新程序的内容替换。

##	内核空间加载与分析

内核在获取到新程序的文件后，开始了真正的加载工作。

-	识别与解析：内核首先读取ELF文件头部（Header），检查文件开头的魔数（`\x7fELF`），确认这是一个合法ELF文件。

-	映射（Map）内存段：根据ELF程序头表（Program Header Table），内核会解析出类型为`PT_LOAD`的段。这些段包含程序代码（`.text`）和数据（`.data`），内核会通过`mmap`相关机制将它们映射到新进程的内存中。

-	处理解释器（PT_INTERP）：加载完主程序后，内核会检查程序头中是否有`PT_INTERP`段。该段主要存放动态链接器路径。

	-	有`PT_INTERP`段：说明这是一个动态链接的可执行文件。内核会自动将该段指定的动态链接器（例如LoongArch下的`ld-linux-loongarch-lp64d.so.1`）加载到内存，并准备将控制权移交给它。

	-	无`PT_INTERP`段：对于静态链接的可执行文件，内核加载工作就此完成，并直接跳转到文件中指定的入口点（`e_entry`）。

-	内核会为新进程设置栈空间，并将一些关键辅助信息（Auxiliary Vector）放在栈上，例如程序头地址（`AT_PHDR`）、动态链接器基址（`AT_BASE`）等，供用户态程序和动态链接器使用。

##	用户态的动态链接器 (ld.so)

如果是动态链接程序，CPU会跳转到动态链接器入口点开始执行。

-	自我初始化：动态链接器首先执行自身重定位，确保自己可以正常运行。

-	加载共享库：动态链接器读取主程序的`.dynamic`段，找到所有依赖的共享库（`DT_NEEDED`条目），然后递归加载并映射到内存中。

-	重定位和符号解析：这是核心步骤。动态链接器会解析所有未定义符号，并将它们绑定到正确内存地址。这包括GOT（全局偏移表）和PLT（过程链接表）的初始化。默认情况下，函数地址解析是延迟进行的（Lazy Binding），即函数第一次被调用时才解析；也可以设置环境变量`LD_BIND_NOW=1`，让链接器在程序启动时一次性解析所有符号。

-	移交控制权：完成所有链接工作后，动态链接器从栈上获取主程序入口点地址，然后跳转过去，程序开始正式运行。

##	程序入口与最终启动

无论是静态链接还是动态链接，最终都会跳转到ELF头中定义的入口点（`e_entry`）。在基于glibc的C/C++程序中，入口点并不是`main`函数，而是一个名为`_start`的汇编例程。

LoongArch架构中的`_start`主要完成以下工作：

-	按照LoongArch ELF ABI规范，准备传给`__libc_start_main`函数的各项参数，例如`main`函数地址、命令行参数`argc`/`argv`、环境变量等。

-	调用glibc的`__libc_start_main`函数。

-	由`__libc_start_main`负责初始化C运行环境（如I/O、线程等），并调用`main`函数。

总体来看，操作系统加载ELF文件的过程可分为几个层次：内核负责底层文件解析、内存映射和安全检查；动态链接器作为中间层处理库依赖和重定位；最后，`_start`为`main`函数执行做准备。

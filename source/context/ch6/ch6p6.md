#	操作系统加载ELF文件

在LoongArch架构中，操作系统加载并运行一个ELF文件，主要通过execve()系统调用触发，整个过程从内核态的解析、加载，再到用户态动态链接器的接管，最终跳转到程序入口点。

##	系统调用入口

当Shell中输入一个命令后，Shell会通过 fork() 创建一个新的进程，然后在新进程中调用 execve() 系统调用，并传递程序路径和参数。在内核中，这会触发一系列调用链，最终指向内核的 二进制格式处理程序（binfmt）。

execve() 调用链：sys_execve() -> do_execve() -> search_binary_handler() -> load_elf_binary()。

在这个调用过程中，Linux内核会将当前进程的旧地址空间完全销毁，用新程序的内容替换。

##	内核空间加载与分析

内核在获取到新程序的文件后，开始了真正的加载工作。

-	识别与解析：内核首先读取ELF文件的头部（Header），检查文件开头的魔数（\x7fELF），确认这是一个合法的ELF文件。

-	映射( Map )内存段：根据ELF的 程序头表（Program Header Table） ，它会解析出类型为 PT_LOAD 的段。这些段包含了程序的代码(.text)和数据(.data)，内核会通过mmap系统调用将它们精确地映射到新进程的内存中。

-	处理解释器(PT_INTERP)：加载完主程序后，内核会检查程序头中是否有 PT_INTERP 段。这个段主要存放着动态链接器的路径。

	-	有 PT_INTERP 段：说明这是一个动态链接的可执行文件。内核会自动加载该段指定的动态链接器（例如 LoongArch 下的 ld-linux-loongarch-lp64d.so.1）到内存中，并准备将控制权移交给它。

	-	无 PT_INTERP 段：对于静态链接的可执行文件，内核的加载工作就此完成，它将直接跳转到文件中指定的入口点(e_entry)。

-	内核会为新进程设置好栈空间，并将一些关键的辅助信息（Auxiliary Vector）放在栈上，例如程序头地址(AT_PHDR)、动态链接器基址(AT_BASE)等，供用户态的程序和动态链接器使用。

##	用户态的动态链接器 (ld.so)

如果是一个动态链接程序，CPU 会跳转到动态链接器的入口点开始执行。

-	自我初始化：动态链接器首先会执行自身的重定位，确保自己可以正常运行。

-	加载共享库：它读取主程序的 .dynamic 段，找到所有依赖的共享库（DT_NEEDED 条目），然后递归地加载它们，映射到内存中。

-	重定位和符号解析：这是核心步骤。动态链接器会解析所有未定义的符号，并将它们绑定到正确的内存地址。这包括 GOT（全局偏移表） 和 PLT（过程链接表） 的初始化。默认情况下，函数地址的解析是延迟进行的（Lazy Binding），即函数第一次被调用时才解析；也可以设置环境变量 LD_BIND_NOW=1，让链接器在程序启动时一次性解析所有符号。

-	移交控制权：完成所有链接工作后，动态链接器会从栈上获取主程序的入口点地址，然后跳转过去，程序开始正式运行。

##	程序入口与最终启动

不管是静态还是动态链接，最终都会跳转到ELF头中定义的入口点（e_entry）。在基于glibc的C/C++程序中，入口点并不是main函数，而是一个名为_start的汇编例程。

LoongArch架构中的 \_start 主要做了这些事：

-	按照LoongArch ELF ABI规范，精心准备好传给__libc_start_main函数的各项参数，例如main函数的地址、命令行参数argc/argv、环境变量等。

-	调用glibc的 \_\_libc_start_main 函数。

-	由 \_\_libc_start_main 负责初始化C运行环境（如I/O、线程等），并调用我们熟知的 main 函数。

总结，操作系统调用ELF文件的整个过程，分为几个层次：内核负责最底层的文件解析、内存映射和安全检查；动态链接器作为中间层处理复杂的库依赖和重定位；最后，\_start 为 main 函数的执行做准备。

#	ELF文件格式解析

ELF文件是Linux系统下常用的一种目标文件存储格式。典型目标文件主要有以下3类。

-	可重定位文件（Relocatable File）：尚未经过链接的目标文件。其内容包含编译器生成的汇编代码和数据，可与其他可重定位文件一起链接形成可执行文件或动态库。通常文件扩展名为`.o`。

-	可执行文件（Executable File）：经过链接器链接、可被Linux系统直接执行的目标文件。其内容包含可运行的机器指令和数据。通常此类文件无扩展名。

-	动态库文件（Shared Object File）：动态库文件是共享程序代码的一种方式，其内容与可重定位文件类似，包含可用于链接的代码和数据，可视为多个可重定位文件的集合。通常文件扩展名为`.so`。动态库参与两个过程：链接时，链接器将其与其他可重定位文件、动态库一起链接形成可执行文件；运行时，动态链接器在需要时将动态库文件加载到内存。

ELF文件中存放的是可在处理器上执行的二进制指令和数据。不同系统架构下，ELF内部格式和数据处理方式会略有差异，但基本格式如图6-1所示。

##	ELF文件头

ELF文件头描述目标文件的组织形式，是对目标文件基本信息的概括，包括字长和字节序、ELF文件头大小、目标文件类型、机器类型、节头表/程序头表的大小和数量、程序入口点等。ELF文件头信息必须位于目标文件最开始的位置。可以使用工具`readelf`查看可重定位文件`hello.o`的ELF头信息。
``` shell
$ readelf -h hello.o
ELF 头：
Magic：  7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00
Class:                           ELF64
Data:                            2补码，小端序(little endian)
Version:                         1(current)
OS/ABI:                          UNIX - System V
ABI Version:                     0
Type:                            REL（可重定向文件）
Machine:                         LoongArch
Version:                         0x1
入口点地址：                       0x0
程序头起点：                       0(bytes into file)
Start of section headers:        856 (bytes into file)
标志：                            0x3, LP64
本头的大小：       64（字节）
程序头大小：       0（字节）
Number of program headers:         0
节头大小：         64（字节）
节头数量：         13
字符串表索引节头： 10
```
这里，`readelf`的参数`-h`代表header，表示查看目标文件头信息。头信息中部分字段说明如下。

-	魔数（Magic）：用于确定文件格式和类型。这里魔数的前4字节`7f 45 4c 46`标识这是一个ELF格式文件。第5字节`02`表示文件运行在64位体系架构（`01`表示32位）。第6字节`01`表示小端序（`02`表示大端序），也可通过后面的Data信息获知。第7字节`01`表示ELF版本。后面的9字节未定义。

-	Type：标识当前文件类型，具体可为可重定位文件、可执行文件、动态库文件中的一种。当前头信息显示目标文件类型为可重定位文件。可重定位文件的入口点地址通常为0x0，而且没有程序头，因此程序头起点、程序头大小和Number of program headers都显示为0。

-	Machine：标识处理器架构。当前结果LoongArch表示龙芯架构，其值为258。

-	Start of section headers：标识节头表数据在当前文件中的起始位置。

-	标志：用于特定于处理器的ABI类型。对于龙芯处理器，ABI类型可以是LP64s、LP64f、LP64d、ILP32s、ILP32f、ILP32d中的一种。

一般来说，C语言程序编译生成的机器指令存放在代码段（`.text`），已初始化的全局变量和局部静态变量保存在数据段（`.data`），未初始化的全局变量和局部静态变量保存在`.bss`段。一些字符串常量、不可改变的变量（使用`const`修饰）则存放在只读数据段（`.rodata`）。这种分段存储有多方面好处。程序运行时，不同段的内容被映射到内存中具有不同管理权限（如只读、可写、可执行等）的区域，首先可以提升安全性（防止指令段数据被修改）；其次可以节省内存（当系统运行多个该程序时，只需共享一份指令段）；同时也有利于性能提升（提升缓存命中率）。

程序中的段类型以`SHT_`开头，如`SHT_NULL`、`SHT_SYMTAB`等，但`readelf`显示时省略了`SHT_`。

3.	段标志

段标志（Flag）在上面段信息中显示为旗标，用于表示该段在进程虚拟空间中的访问属性。常见访问属性包括可写（Write）、可执行（Execute）、可分配（Alloc），而所有段默认可读。例如，上面段信息中`.text`段的段标志AX表示Alloc+Execute，即该段在内存中可分配且可执行，但不可写。如果程序执行过程中错误地向此段写数据，就会触发SIGSEGV异常。`.data`段、`.bss`段的标志WA表示Write+Alloc，即该段可写并可分配空间；`.symtab`段、`.strtab`段标志为空，表示该段没有可写权限和可执行权限。

4.	段地址、偏移量和大小

段地址（在上面段信息中显示为地址）记录当前段被加载到内存后的虚拟起始地址。由于当前`hello.o`文件尚未重定位，其在进程中的位置还不确定，因此当前所有段地址都显示为0000000000000000。如果读取最终的可执行文件`hello`，段地址信息将显示为类似如下的非零有效地址值。

``` shell
 [10] .text  PROGBITS  00000001200008f0  000008f0 000270   AX   0   0   16
```
这里的虚拟地址就是`.text`段最终被加载到内存后的虚拟地址。尽管理论上进程可以使用一定范围内的虚拟地址空间，但一般情况下进程并不能使用全部虚拟地址空间，系统通常会预留一部分虚拟地址空间用于自身配置。

偏移量（Offset）用于表示该段在ELF文件中的偏移。例如，上面读取`hello.o`段表信息中`.text`段的Offset值为0x40（64字节），而`readelf -h hello.o`显示“本头的大小：64（字节）”，说明`hello.o`的ELF文件中，头信息之后紧接着就是`.text`段。

大小（Size）用于表示该段大小。例如，上面信息中`.text`段大小为000040（即十六进制0x40），转换为十进制后表示代码段占用64字节；而`.data`段、`.bss`段显示大小均为000000，表示这些段没有内容，不占据文件空间。

5.	段地址对齐

如果某段有地址对齐要求，那么段地址对齐字段（在上面段信息中显示为对齐）就指定了地址对齐方式。例如，上面段信息中`.text`段的对齐值为4，表示该段在内存中的起始地址必须按4字节对齐，即该段数据在内存中的起始地址必须能被4整除。当对齐值为0或1时，可认为该段没有额外对齐要求。上面段表信息中的`.bss`段、`.data`段对齐值都为1，说明这些段在内存中存放时没有额外对齐要求。

##	可执行文件中的段和程序头表

可重定位文件中描述Section属性的结构称为节头表（Section Header Table），而可执行文件和动态库文件中描述Segment属性的结构称为程序头表（Program Header Table），它指导系统如何将多个段（Segment）加载到内存空间。前面提到，Segment可以看作多个可重定位文件（`.o`文件）中属性相似的Section的合并，即一个Segment包含一个或多个属性相似的Section。这里的属性相似主要指权限（在段标志Flag中指定）。链接器会将多个`.o`文件中具有可执行权限的`.text`和`.init`段放入最终可执行文件的同一个Segment中，这样可以节省内存空间。因为ELF文件加载时以系统页为单位，如果一个ELF文件中有10个段且每个段大小都小于一个内存页，那么按一个段占据一个内存页计算，当前进程就需要10个内存页。而如果链接器将具有相同权限的段合并映射，当前进程所需内存页通常会少于10个，从而更充分地利用内存页并减少内存碎片。例如，段表信息中的`.data`段和`.bss`段具有相同权限WA，就可以存放在同一个页或多个连续页上。程序头表记录了这些具有相同权限的段被合并后的信息。

可以使用`readelf -S`或`readelf -l`查看可执行文件`hello`中的段信息和程序头表信息。

##	符号和符号表

在目标文件中，函数和变量统称为符号（Symbol）。这里的变量指不占用函数栈空间的全局变量或静态局部变量，不包括函数内的普通局部变量。函数名和变量名统称为符号名（Symbol Name）。每一个可重定位目标文件中都会有一个符号表（Symbol Table），用于记录目标文件中使用到的所有符号及其符号名、符号类型、符号大小等信息。有了符号和符号表，编译器在链接阶段才能正确解析多个目标文件中变量、函数之间的关系，并配合重定位表完成重定位，最终将多个目标文件正确合并为可执行文件或动态库文件。

符号按定义的种类可以分为局部符号、全局符号、外部符号和段符号这4类。

-	局部符号：对应C语言函数内部定义的静态局部变量和静态函数，例如下面的变量a和函数`fun()`。
``` c
static int a;
static int fun(){
}
```
这里有两个局部符号，符号名分别为a和fun。这类符号只在编译单元内部（当前目标文件内部）可见。

-	全局符号：定义在当前目标文件中，但可以被其他文件引用的变量和函数。例如，下面C语言程序中定义了符号名分别为`global_var`和`main`的全局符号。
``` c
int global_var;
int main(int arg,char* arg[]){
}
```

-	外部符号（External Symbol）：在当前目标文件中引用、但定义在其他目标文件或库中的全局符号。例如常用的`printf`函数（定义在libc中的符号）或使用`extern`声明的变量。

-	段符号：由编译器产生的`.text`、`.data`等段名也称为符号。

目标文件中符号表所在的段为`.symtab`。如果是可执行目标文件，还会有一个`.dynsym`段用于存放动态符号表。可以使用`readelf -s 文件名`查看目标文件中的符号表信息。例如下面的C语言代码：
``` c
#include <stdio.h>
char* str="HELLO";
int global_var;
int main(){
	int a = 0,b = 0;
	static int static_a = 0;
	printf("%s %d\n",str,a+b+static_a);
	return 0;
}
```
其编译后生成的可重定位文件`hello.o`中符号表信息如下：
``` shell
$ readelf -s hello.o
Symbol table '.symtab' contains 13 entries:
Num:   Value          Size  Type    Bind     Vis    Ndx    Name
0: 0000000000000000    0   NOTYPE   LOCAL  DEFAULT  UND
1: 0000000000000000    0   SECTION  LOCAL  DEFAULT     1
2: 0000000000000000    0   SECTION  LOCAL  DEFAULT     3
3: 0000000000000000    0   SECTION  LOCAL  DEFAULT     5
4: 0000000000000000    0   SECTION  LOCAL  DEFAULT     6
5: 0000000000000000    4   OBJECT    LOCAL  DEFAULT     5    static_a
6: 0000000000000000    0   SECTION  LOCAL  DEFAULT     7
7: 0000000000000000    0   NOTYPE   LOCAL  DEFAULT     6    .LC0
8: 0000000000000000    0   SECTION  LOCAL  DEFAULT     8
9: 0000000000000000    8   OBJECT    GLOBAL DEFAULT    3     str
10: 0000000000000000    4   OBJECT    GLOBAL DEFAULT    COM    global_var
11: 0000000000000000   60  FUNC      GLOBAL DEFAULT     1     main
12: 0000000000000000    0   NOTYPE   GLOBAL DEFAULT    UND    puts
```

从上面的信息可以看出，`hello.o`文件中包含若干个符号，编号显示在Num列。每个符号都有如下属性。

-	符号值（Value）：每个符号都有一个对应值。如果此符号是函数或变量，其符号值通常是函数或变量的虚拟地址。上面`hello.o`是尚未重定位的ELF文件，因此符号值多为0。在可执行文件中，符号值可能是符号的虚拟地址、符号所在函数偏移等。但对于COM类型的符号，Value列表示其对齐方式。

-	符号大小（Size）：对于变量，符号大小就是数据类型的大小，单位是字节。例如，上述C语言示例中的变量`static_a`数据类型为`int`，因此大小为4字节。字符串指针`str`在LA64架构上为8字节。对于函数，符号大小就是该函数被编译后所有机器指令占用的字节数。例如符号`main`大小为60字节，龙芯指令集中每条指令为4字节，可以推算出`main`函数被编译后共有15条机器指令。

-	符号类型(Type)分为如下种类。

	-	NOTYPE：未知符号类型。包括目标文件中用于条件跳转的标签、在外部定义的符号等。

	-	OBJECT：数据对象，比如C语言变量、字符串、数组等。

	-	FUNC：函数或其他可执行代码。

	-	SECTION：一个段。

	-	FILE：文件名。
-	绑定信息（Bind）分为如下种类。

	-	LOCAL：局部符号。例如上面定义的静态局部变量`static_a`。

	-	GLOBAL：全局符号。包括本文件内定义的全局变量`global_var`、`str`、`main`和外部函数`printf`。

	-	WEAK：弱引用符号。在这里没有体现。对于C/C++语言，编译器默认将函数和已初始化的全局变量视为强符号，而将未初始化的全局变量和使用`__attribute__((weak))`定义的变量视为弱符号。

-	Vis：可扩展符号功能，暂未定义其具体功能，可忽略。

-	符号所在段（Ndx）：如果符号定义在本目标文件中，那么该成员表示符号所在段在段表中的下标。例如静态变量`static_a`所在段索引为4。Ndx还有如下3种特殊值。

	-	UND：未定义。通常表示这是一个外部符号，不在本目标文件中定义。例如定义在libc库中的`printf`函数，或使用`extern`声明的外部变量。

	-	ABS：表示该符号包含一个绝对值，比如符号hello.c。

	-	COM：表示该符号是未初始化的全局符号，例如变量`global_var`。

-	符号名（Name）：符号表的最后一列，如`static_a`、`.LC0`、`str`、`global_var`、`main`和`puts`。还有一些符号没有名字，只能通过编号识别。没有名字的符号通常是段（可从Type列的SECTION看出）或未知符号类型。

##	重定位和重定位表

重定位包括链接时重定位和加载时重定位。链接时重定位指编译器在链接阶段将多个可重定位目标文件合并为一个可执行目标文件时，对文件中程序数据和函数调用指令进行地址确定的过程。链接时重定位不包括动态库中数据加载和函数调用指令的定位，这一过程需要在加载时重定位完成。加载时重定位主要针对动态库，即程序运行过程中加载动态库时，对动态库中函数调用和数据引用的绝对地址进行确定。

对于同一个文件内的函数调用，由于函数之间的相对位置是固定的（链接时同一文件内的函数通常连续存放），因此一般不存在需要重定位的情况。重定位主要处理多个文件之间或多个模块之间（这里模块指动态库或可执行目标文件）的函数调用和数据引用。下面列举一个简单的链接时重定位示例：在如下两个C语言文件中，`a.c`调用了`b.c`中的`temp`函数，具体内容如下：
``` c
/* a.c */
extern void temp();
int main(){
	temp();
}
```
``` c
/* b.c */
void temp(){
	// do nothing
}
```
在编译器尚未进行重定位之前，目标文件`a.o`和`b.o`中的指令信息为
``` shell
$objdump -d a.o
Disassembly of section .text:
0000000000000000 <main>:
0:			02ffc063 	addi.d 		$r3, $r3, -16(0xff0)
4:			29c02061 	st.d 		$r1, $r3, 8(0x8)
8: 			27000076 	stptr.d 	$r22, $r3, 0
c:			02c04076 	addi.d 		$r22, $r3, 16(0x10)
10: 		54000000 	bl 			0 		# 10 <main + 0x10>
...
$objdump -d b.o
Disassembly of section .text:
0000000000000000 <temp>:
0:			02ffc063 	addi.d 		$r3, $r3, -16(0xff0)
4:			29c02076 	st.d 		$r22, $r3, 8(0x8)
...
```
前面介绍过，链接前的可重定位目标文件中所有段的起始地址都是0。当前`a.o`文件的代码段（`.text`）中只有函数`main`，因此函数`main`的起始地址为0000000000000000；`b.o`文件的代码段中只有函数`temp`，因此函数`temp`的起始地址也为0000000000000000。相对跳转指令`bl 0`表示要调用函数`temp`，但这里跳转目标地址为0，说明此时还不清楚函数`temp`的实际位置。待链接时函数`temp`地址确定后，需要重新修正这条指令。

再看编译器链接后生成的可执行目标文件`a.out`中的相关函数地址和指令情况：
``` shell
$objdump -d a.out
Disassembly of section .text:
000000000000066c <main>:
66c:		02ffc063 	addi.d 		$r3, $r3, -16(0xff0)
670:		29c02061 	st.d 		$r1, $r3, 8(0x8)
674: 		27000076 	stptr.d 	$r22, $r3, 0
678:		02c04076 	addi.d 		$r22, $r3, 16(0x10)
67c: 		54001c00 	bl 			28(0x1c) 		
...
0000000000000698 <temp>:
698:		02ffc063 	addi.d 		$r3, $r3, -16(0xff0)
69c:		29c02076 	st.d 		$r22, $r3, 8(0x8)
...
```
可以看到，在链接后的目标文件`a.out`中，函数`main`和`temp`的起始地址都已经确定，分别为0x00000066c和0x000000698。用于调用函数`temp`的相对跳转指令`bl`中的地址也已经修正，由`bl 0`变为`bl 28`。当前PC（0x00000067c）加上偏移值28（0x1c）后的地址恰好为0x000000698，即函数`temp`的起始地址。

编译器链接过程中最主要的两件事是地址分配和重定位。地址分配过程会处理所有输入文件（这里指`a.o`和`b.o`），获取所有符号信息、段长度、属性等信息，并据此合并相同属性的段、确定符号地址，例如确定函数`main`和`temp`的起始地址为0x00000066c和0x000000698。重定位过程在地址分配基础上，对数据加载指令或函数调用指令进行地址确定并修改，例如将指令`bl 0`修改为`bl 28`。

但并不是所有数据加载指令或函数调用指令都需要修改。那么，哪些指令需要修改、如何修改？这就需要目标文件中的重定位表。在可重定位目标文件中，每一个包含需要地址修正指令的段，都会对应一个重定位段。例如，目标文件`a.o`的代码段`.text`中有需要修正的指令`bl`，那么`a.o`中就会有一个`.rela.text`段，段内记录需要地址修正的指令所在位置、修正方法、修正后的符号名称等信息。如果数据段`.data`中也有需要地址修正的内容，还会有相应的重定位段与之对应。重定位表记录了所有这些信息。

这里使用命令`objdump -r`查看`a.o`中的重定位信息：
``` shell
$ objdump -r a.o
a.o：   文件格式 elf64-loongarch
RELOCATION RECORDS FOR [.text]:
OFFSET    TYPE      VALUE
0000000000000010 R_LARCH_SOP_PUSH_PLT_PCREL  temp
```
这说明`a.o`的代码段中有需要地址修正的指令，其在当前目标文件中的偏移地址为0x10，即上面`a.o`中的指令：
``` shell
10: 	54000000 	bl 	0 	#	10<main + 0x10>
```
符号名`temp`指明指令地址修正后指向的目标是函数`temp`。地址修正类型（也称重定位类型）`R_LARCH_SOP_PUSH_PLT_PCREL`指明如何进行地址修正。每一种体系架构都有一套独立的地址修正类型，这属于架构ABI范畴。通过查看龙芯架构参考手册的ABI部分可知，这里的`R_LARCH_SOP_PUSH_PLT_PCREL`表示修正方式是利用跳转目标地址与当前PC的相对寻址修正。这里跳转目标为函数`temp`，其在链接过程地址分配后确定的地址为0x000000698，当前PC地址为指令`bl 0`所在地址0x00000067c。因此，相对寻址修正后的值为0x1c（0x000000698-0x00000067c），修正后的跳转指令`bl`机器指令由之前的54000000修改为54001c00。
